# task_0003: AI 地上施設利用

## 状態

設計レビュー待ち

## 目的

地上帰還後の施設利用を AI（Goal/Plan/Action 体系）で制御できるようにする。`ActorAiContext` に施設位置参照を追加し、`AdventurerAiPolicy` に Recovering 状態向けの施設選択ロジックを実装する。

## 精査後の確定方針

実装時はこのタスク内の「理想設計」を採用する。既存実装に合わせた `AdventurerGuild` / `GroundMap` の直接参照、`ShouldUseGeneralStore()` などの施設別メソッド、`Recovering` 状態専用分岐は移行前の参考として扱い、最終実装の目標にはしない。

確定方針:

- AI は `FacilityNeed` を列挙し、`FacilityNeedSelector` で次に解決する Need を 1 つ選ぶ。
- `ActorAiContext` は `FacilityCatalogSnapshot` / `GroundNavigationSnapshot` / `ActorAdventureIntent` を持つ読み取り専用 Context にする。
- AI は施設座標を計算しない。`GroundFacilityNavigationPlanner` が `FacilityInteractionPoint` から `NavigationIntent` を生成する。
- `ActorPlan` は `ResolveFacilityNeed` / `PrepareNextAdventure` / `EnterDungeon` を表せる形へ拡張する。
- `Visit済み` 状態は追加しない。Need が解消されれば次回評価で同じ施設は選ばれない。

「施設を利用して回る」は必須巡回ではない。AI が Actor の現在状態・所持品・購入可否・次の冒険目的から必要と判断した施設だけを選ぶ。用事が終わった施設を「訪問済みフラグ」だけで再訪抑止するのではなく、用事そのものが解消されていることを条件として次の施設判断から外す。

具体的には以下を実現する。

- `ActorAiContextFactory` で AI 判断用 Snapshot を生成する
- `GroundFacilityNeedEvaluator` で `RecoverAtInn` / `SellGeneralGoods` / `RefillPotions` / `SellUnusedEquipment` / `UpgradeWeapon` / `UseTavern` の Need を列挙する
- `FacilityNeedSelector` で優先度・距離・期待効果から 1 つの Need を選ぶ
- `GroundFacilityNavigationPlanner` で施設入口の `NavigationIntent` を作成する
- `ActorAiDecisionApplier` で Plan / Action の再設定ルールを一元管理する

## 利用するLighthouseパターン

- `[P9] ProductLifetimeScope へのサービス登録` — `AdvanceActorAiOrchestrator` の依存注入確認

## 前提

task_0001 と task_0002 が完了していること（`FacilityCatalog` / `FacilityBuildingRegistry` から Inn / Tavern / GeneralStore / EquipmentShop と各 `FacilityInteractionPoint` を参照できること）。

## 設計

### 理想設計の前提

互換性維持は考慮しない。現在の `SellItemsUseCase`、`UpdateEquipmentUseCase`、`ProcessFacilityUsageUseCase`、Inn 固有予約処理が分散している状態を前提にせず、地上帰還後の意思決定は以下の 3 層に再設計する。

- `AdventurerGroundGoalPolicy`: Actor の状態・所持品・所持金・施設在庫・次回冒険目的から、必要な施設利用目標を 1 つ選ぶ純粋なポリシー。
- `GroundFacilityNavigationPlanner`: 施設目標から入口接触位置への移動 Action を生成する。NavMesh / A* の詳細はここより下の移動サービスに隠蔽する。
- `FacilityInteractionOrchestrator`: Actor が入口接触状態になった施設利用目標を実行し、売却・購入・回復・食事・装備切替を 1 つのトランザクションとして完了させる。

AI は「どの施設に行くか」ではなく「どの未解決の用事を解決するか」を選ぶ。施設はその用事の実行場所として解決される。これにより、同じ施設に複数の用途が追加されても `ShouldUse...()` のハードコードを増やさずに済む。

### ActorAiContext の変更

`Guild` と `GroundMap` を追加する。

**理想設計**

`ActorAiContext` は巨大な `IGameWorldState` をそのまま持たず、AI 判断に必要な読み取り専用スナップショットだけを持つ。

```csharp
public sealed class ActorAiContext
{
    public Actor Actor { get; }
    public GroundNavigationSnapshot Navigation { get; }
    public FacilityCatalogSnapshot Facilities { get; }
    public ActorAdventureIntent NextAdventureIntent { get; }
    public int CurrentTick { get; }

```

- `FacilityCatalogSnapshot` は施設位置、入口接触位置、施設在庫、売買価格、利用可能サービスをまとめる。
- `NextAdventureIntent` は次の冒険で必要な回復量・最低ポーション数・推奨武器スコアなど、AI が施設利用を判断するための目的を表す。
- AI は `AdventurerGuild` の可変 Entity を直接見ない。施設在庫や価格の変更は Interaction 実行時にのみ行う。

### AdvanceActorAiOrchestrator の変更

`ExecuteAsync()` が `IGameWorldState` を受け取れるように変更し、コンテキスト生成時に `Guild` と `GroundMap` を渡す。

```csharp
// 変更前
public UniTask ExecuteAsync(IEnumerable<Actor> actors, float ...) 

// 変更後（IGameWorldState を追加）
public UniTask ExecuteAsync(IEnumerable<Actor> actors, IGameWorldState worldState, float ...)
```

呼び出し元（`WorldSimulationOrchestrator` 等）も合わせて修正する。

**理想設計**

`AdvanceActorAiOrchestrator` は `IGameWorldState` を各 Policy に流すのではなく、AI 専用の Snapshot を構築して Policy に渡す。Snapshot 構築は `ActorAiContextFactory` に分離する。

```csharp
public UniTask ExecuteAsync(IGameWorldState worldState, ActorSimulationTick tick)
{
    actorBuffer.Clear();
    actorSelector.CollectAiControlledActors(worldState, actorBuffer);

    foreach (var actor in actorBuffer)
    {
        var context = contextFactory.Create(worldState, actor, tick);
        var decision = groundGoalPolicy.Evaluate(context);
        actorAiDecisionApplier.Apply(actor, decision);
    }
}
```

- AI 評価対象の抽出、Context 生成、Policy 評価、Decision 反映を分離する。
- `AdvanceActorAiOrchestrator` は施設種類を知らない。
- `ActorAiDecisionApplier` が「既存 MoveAction と同じ目標なら再設定しない」などの Action 更新規則を一元管理する。

### AdventurerAiPolicy の変更

**EvaluateMidTerm()**

Recovering 状態の分岐を追加する。

```csharp
public ActorAiDecision EvaluateMidTerm(ActorAiContext context)
{
    var actor = context.Actor;
    if (actor.Behavior is not AdventurerBehavior behavior) { ... }

    if (behavior.LifecycleState == AdventurerLifecycleState.Recovering
        || behavior.LifecycleState == AdventurerLifecycleState.WaitingForInn)
    {
        return EvaluateRecoveringMidTerm(context, actor, behavior);
    }

    // 従来の Prepare プラン設定（非 Recovering 状態）
    ...
}

ActorAiDecision EvaluateRecoveringMidTerm(ActorAiContext context, Actor actor, AdventurerBehavior behavior)
{
    var guild = context.Guild;

    // HP が低い → Inn で回復
    if (actor.HpRatio < RecoverHpThreshold)
    {
        var inn = guild.Facilities.FirstOrDefault(f => f.Type == FacilityType.Inn);
        if (inn != null)
            return new ActorAiDecision(null, new ActorPlan(ActorPlanType.Recover, inn.Id, 0), null);
    }

    // 雑貨屋: 不要な非装備アイテム売却、ポーションを2個まで補充できる場合
    var generalStore = FindFacility(guild, FacilityType.GeneralStore);
    if (generalStore != null && ShouldUseGeneralStore(actor, generalStore))
        return new ActorAiDecision(null, new ActorPlan(ActorPlanType.UseFacility, generalStore.Id, 0), null);

    // 装備屋: 未装備装備売却、またはより強い武器を購入できる場合
    var equipmentShop = FindFacility(guild, FacilityType.EquipmentShop);
    if (equipmentShop != null && ShouldUseEquipmentShop(actor, equipmentShop))
        return new ActorAiDecision(null, new ActorPlan(ActorPlanType.UseFacility, equipmentShop.Id, 0), null);

    // Tavern は「利用すべき理由」が仕様・状態として存在する場合のみ選ぶ。
    var tavern = FindFacility(guild, FacilityType.Tavern);
    if (tavern != null && ShouldUseTavern(actor, behavior, tavern))
        return new ActorAiDecision(null, new ActorPlan(ActorPlanType.UseFacility, tavern.Id, 0), null);

    // 必要な施設利用なし → Prepare
    return new ActorAiDecision(null, new ActorPlan(ActorPlanType.Prepare, default, 0), null);
}
```

`RecoverHpThreshold`、各 `ShouldUse...()` の実装詳細は Codex 側で判断してよいが、以下の制約を守ること。

- `RecoverHpThreshold` は定数または設定値として扱う（マジックナンバー禁止）
- GeneralStore の利用判断は「売却可能な非装備アイテムが残っている」「ポーション所持数が 2 個未満、店舗在庫と所持金が足りる」のいずれかで行う
- EquipmentShop の利用判断は「売却可能な未装備装備が残っている」「現在装備より強い武器を店舗在庫と所持金で購入できる」のいずれかで行う
- Tavern は現時点で利用理由が仕様化されていなければ強制訪問しない。必要状態の新規追加が必要な場合は Claude Code に確認する
- 「訪問済みフラグ」を主条件にしない。施設利用後は売却済み・購入済み・回復済みなどの実データ変化により `ShouldUse...()` が false になる設計にする

**理想設計**

`AdventurerAiPolicy` に `ShouldUseGeneralStore()` / `ShouldUseEquipmentShop()` のような施設別メソッドを並べない。代わりに、施設利用候補を生成して優先度順に選ぶ。

```csharp
public ActorAiDecision EvaluateGroundRecovery(ActorAiContext context)
{
    facilityNeedBuffer.Clear();
    groundFacilityNeedEvaluator.CollectNeeds(context, facilityNeedBuffer);

    if (facilityNeedBuffer.Count == 0)
    {
        return ActorAiDecision.Plan(ActorPlan.PrepareNextAdventure());
    }

    var selected = facilityNeedSelector.SelectBest(context, facilityNeedBuffer);
    return ActorAiDecision.Plan(ActorPlan.ResolveFacilityNeed(selected.NeedId, selected.FacilityId));
}
```

`FacilityNeed` は以下のような値オブジェクトにする。

```csharp
public readonly struct FacilityNeed
{
    public FacilityNeedType Type { get; }
    public Guid FacilityId { get; }
    public int Priority { get; }
    public int ExpectedGoldDelta { get; }
    public int ExpectedPowerDelta { get; }
    public bool IsResolvedByCurrentState { get; }
}
```

初期実装で必要な `FacilityNeedType`:

- `RecoverAtInn`: HP/MP が次回冒険に不足している。
- `SellGeneralGoods`: 不要な非装備アイテムがある。
- `RefillPotions`: ポーション所持数が 2 未満で、在庫・所持金が足りる。
- `SellUnusedEquipment`: 不要な未装備装備がある。
- `UpgradeWeapon`: 現在装備より強い武器を購入可能。
- `UseTavern`: 明確なゲーム仕様上の理由がある場合のみ。

この方式では「訪問したか」は状態として不要になる。売却・購入・回復が完了した結果、次の評価で同じ `FacilityNeed` が生成されなければ再訪しない。

**EvaluateShortTerm()**

現在プランが Recover / UseFacility の場合、対応する施設の入口接触位置を MoveTo アクションとして設定する。

```csharp
// Recovering 状態で現在プランが施設移動系の場合
if (currentPlan.Type == ActorPlanType.Recover || currentPlan.Type == ActorPlanType.UseFacility)
{
    var facility = context.Guild.Facilities.FirstOrDefault(f => f.Id == currentPlan.TargetId);
    if (facility == null) return ActorAiDecision.Empty;

    var targetPos = FacilityEntranceNavigationTargetCalculator.Calculate(
        context.GroundMap.Layer,
        facility);
    return new ActorAiDecision(null, null, ActorAction.MoveTo(targetPos));
}
```

施設への移動先は入口タイル中心そのものではなく、入口タイル中心から建物の向き（`BuildingFacingDirection`）へ `CellSizeMeters * 0.5f` だけずらした接触位置にする。NavMesh が建物メッシュに阻まれて入口タイル中心へ入れない場合でも、入口に触れて入室したように見える位置を目標にするため。

このオフセット目標を使う場合、入室判定を単純な `layer.ToGridPosition(actor.Position) == facility.EntrancePosition` のみにしないこと。オフセット位置が入口タイル境界または隣接セルに落ちる可能性があるため、施設利用可否と `IsInsideFacility` は「施設入口接触判定」（入口中心またはオフセット目標への距離しきい値）で判定する。

**理想設計**

ShortTerm は Facility の座標計算を直接行わない。現在 Plan が `ResolveFacilityNeed` の場合、`GroundFacilityNavigationPlanner` が `NavigationIntent` を返し、Action はその Intent から生成する。

```csharp
var intent = navigationPlanner.CreateFacilityEntranceIntent(context, currentPlan.TargetFacilityId);
return ActorAiDecision.Action(ActorAction.MoveTo(intent.TargetPosition, intent.ArrivalRadius));
```

- `TargetPosition` は入口中心 + facing 方向半タイル。
- `ArrivalRadius` は施設入口接触判定と同じ値を使う。
- NavMesh / A* で到達不能な場合は、AI Policy ではなく NavigationPlanner が代替入口、待機、失敗理由を返す。
- `ActorAction.MoveTo` は target だけでなく `ArrivalRadius` と `NavigationTargetKind.FacilityEntrance` を持つのが理想。

### 既存プランが完了しているかの判定

AI は毎フレーム `EvaluateShortTerm()` で MoveTo を設定し続けるため、Actor が既に同じ施設入口へ移動中の場合に再設定しないよう、`actor.CurrentAction` が既に `Move` で有効な場合はスキップする判定を設ける。既存の ShortTerm 評価パターンに合わせて実装すること。

**理想設計**

Plan / Action の完了判定は AI Policy ではなく `ActorTaskStateMachine` に寄せる。

- Plan は `Planned → MovingToInteractionPoint → Interacting → Completed / Failed` の状態を持つ。
- 同じ施設入口へ移動中であれば Action を再生成しない。
- 入口接触後は `Interacting` に遷移し、Interaction 完了イベントを受けて Plan を `Completed` にする。
- 次フレームの AI は Completed Plan を見て次の Need を評価する。

これにより、毎フレームの AI 評価と Action 再設定の競合を避けられる。

### GeneralStore / EquipmentShop の理想設計

既存の `SellItemsUseCase`、`UpdateEquipmentUseCase`、`ProcessFacilityUsageUseCase` をスケジュール tick に並列的に呼ぶ構造は廃止し、施設利用時に `FacilityInteractionOrchestrator` が 1 回の処理として実行する。

GeneralStore の Interaction:

1. Actor の不要な非装備アイテムを選定する。
2. 店舗の所持金で買い取れる分を売却する。
3. Actor のポーション所持数が 2 未満なら、店舗在庫・Actor 所持金・インベントリ容量の範囲で 2 個まで購入する。
4. 売却・購入・在庫移動・所持金移動・イベント発行を 1 つの結果として返す。

EquipmentShop の Interaction:

1. Actor の未装備装備から売却対象を選定する。
2. 店舗の所持金で買い取れる分を売却する。
3. 店舗在庫から現在装備より武器スコアが高く、Actor が購入可能な最良武器を 1 つ選ぶ。
4. 購入後、装備切り替えを同じ Interaction 内で行う。
5. 旧装備は Actor のインベントリへ戻す。戻せない場合は購入を行わない。

装備切り替えは「地上に戻ったら自動」ではなく、「拾得直後の即時最適化」と「EquipmentShop 購入後の装備確定」を分ける。理想的には、拾得装備の装備判断も `EquipmentDecisionService` に集約し、帰還中・地上・店舗利用後のどのタイミングでも同じ評価式を使う。
