# task_0004: ライフサイクル・Inn 予約・View

## 状態

設計レビュー待ち

## 目的

ライフサイクルオーケストレーターの Recovering 処理を汎用化し、施設利用を入口接触後のみ行うよう変更し、ActorView を入室状態に応じて非表示にする。

## 精査後の確定方針

実装時はこのタスク内の「理想設計」を採用する。既存実装に合わせた `Recovering` / `WaitingForInn` の拡張、`AdvanceInnRecoveryOrchestrator` への入口チェック追加、`ActorViewData.IsInsideFacility` の追加は移行前の参考として扱い、最終実装の目標にはしない。

確定方針:

- 地上施設利用の進行は `ActorTaskStateMachine` が管理する。
- `Recovering` / `WaitingForInn` を施設利用用の lifecycle state として増やさない。必要なら大枠 state は `OnGround` に寄せる。
- 入口接触判定は `FacilityInteractionPoint.Contains()` に統一する。
- 施設利用は `FacilityInteractionOrchestrator` と `IFacilityInteractionHandler` で実行する。
- Inn 予約、GeneralStore 売買、EquipmentShop 売買と装備切替は施設別 Handler の責務にする。
- View 表示は `ActorPresence` / `ActorViewPresentationState` から導出し、ViewDataStore が入口座標を再判定しない。

具体的には以下を実現する。

- `ActorTaskStateMachine` で `MovingToInteractionPoint` / `Interacting` / `Waiting` / `Completed` を進行する
- `FacilityEntranceDetector` で Actor が接触している `FacilityInteractionPoint` を判定する
- `FacilityInteractionOrchestrator` で現在 Plan に対応する施設利用を開始・進行・完了する
- `FacilityTransactionPlan` / `FacilityTransactionExecutor` で売却・購入・装備切替を一括適用する
- `ActorPresenceService` で Actor の表示状態を決定する

## 利用するLighthouseパターン

このタスクに新規 Lighthouse パターンの利用はない。既存の UseCase / Orchestrator パターンに従って変更する。

## 前提

- task_0001 が完了していること（`FacilityInteractionPoint`、`FacilityBuilding`、`ActorPresence` / `ActorViewPresentationState` が実装済みであること）
- task_0003 が完了していること（AI が `ResolveFacilityNeed` Plan と `NavigationIntent` を生成できること）

## 設計

### 理想設計の前提

互換性維持は考慮しない。`AdvanceInnRecoveryOrchestrator`、`SellItemsUseCase`、`UpdateEquipmentUseCase` のように施設処理が用途別に散っている構造は廃止し、施設入口接触後の処理は `FacilityInteractionOrchestrator` に統合する。

地上施設利用の理想的な責務分担は以下。

- `AdvanceActorLifecycleOrchestrator`: 現在 Action の進行だけを担当する。施設種別も利用内容も知らない。
- `FacilityEntranceDetector`: Actor がどの施設入口に接触しているかを判定する純粋サービス。
- `FacilityInteractionOrchestrator`: 入口接触済み Actor の現在 Plan を読み、該当施設の Interaction を実行する。
- `FacilityInteractionService`: Inn / GeneralStore / EquipmentShop / Tavern の施設別処理を Strategy として持つ。
- `ActorPresenceService`: ActorView 非表示や「施設内にいる」状態を、施設利用 Plan の状態から導出する。

この構造では、Inn だけを特別扱いする予約 UseCase をスケジュール tick で毎回呼ぶのではなく、Actor が Inn の入口へ到達し `RecoverAtInn` Interaction に入った時点で予約・待機・回復を開始する。

### AdvanceActorLifecycleOrchestrator の変更

**Recovering / WaitingForInn の汎用化**

```csharp
case AdventurerLifecycleState.Recovering:
case AdventurerLifecycleState.WaitingForInn:
    await AdvanceGroundMovementAsync(actor, worldState, deltaGameSeconds);
    break;
```

```csharp
async UniTask AdvanceGroundMovementAsync(Actor actor, IGameWorldState worldState, float deltaGameSeconds)
{
    if (!actor.Position.LayerId.Equals(MapLayerId.Ground)) return;
    if (actor.CurrentAction?.Type != ActorActionType.Move) return;
    if (!actor.CurrentAction.HasTargetPosition) return;

    var groundMap = worldState.GroundMap;
    var arrived = moveActorTowardDestinationUseCase.Execute(
        actor,
        actor.CurrentAction.TargetPosition,
        groundMap.Layer,
        groundMap,
        worldGameSettingsRepository.GetActorSimulationSettings().MoveSpeedMetersPerSecond,
        deltaGameSeconds);

    if (arrived)
    {
        actor.CurrentAction.Complete();
        navigationService.InvalidatePath(actor.Id);
    }
}
```

Inn・Tavern・Shop の区別はここに置かない。施設入口接触の検知は各施設ハンドラーの責務。

**理想設計**

Lifecycle は `Recovering` / `WaitingForInn` のような施設由来の状態を直接増やさない。Actor の大枠状態は `OnGround`、現在の作業は `ActorPlan` / `ActorTaskState` で表す。

```csharp
case AdventurerLifecycleState.OnGround:
    await actorTaskStateMachine.AdvanceAsync(actor, worldState, deltaGameSeconds);
    break;
```

`ActorTaskStateMachine` の責務:

- `MovingToInteractionPoint`: `MoveActorTowardDestinationUseCase` で入口接触位置へ移動。
- `Interacting`: `FacilityInteractionOrchestrator` を呼ぶ。
- `Waiting`: Inn 満員など、Interaction が完了待ちになった時だけ待機。
- `Completed`: AI に次 Plan を要求できる状態にする。

`WaitingForInn` は lifecycle state ではなく、`FacilityInteractionStatus.WaitingForCapacity` として表すのが理想。これにより、将来 Tavern や Shop に待機列ができても lifecycle enum を増やさずに済む。

**Recovering → Preparing 遷移**

```csharp
// Recovering 状態で AI が Prepare プランを設定した場合
if (behavior.LifecycleState == AdventurerLifecycleState.Recovering
    && actor.CurrentPlan?.Type == ActorPlanType.Prepare)
{
    behavior.ChangeLifecycleState(AdventurerLifecycleState.Preparing);
    candidateService.SyncActor(actor);
}
```

このチェックは `AdvanceGroundMovementAsync` の前後どちらに置くかを Codex が判断してよい。ただし、同フレームで AI 評価と Lifecycle 処理が実行される順序（`AdvanceActorAiOrchestrator` → `AdvanceActorLifecycleOrchestrator`）を踏まえて決定すること。

**理想設計**

`Recovering → Preparing` という個別遷移は廃止する。地上で必要な `FacilityNeed` がなくなったら AI は `PrepareNextAdventure` Plan を発行し、TaskStateMachine が準備処理を完了した時点で `GoingToDungeon` に遷移する。

```text
OnGround
  ResolveFacilityNeed*  // 0回以上
  PrepareNextAdventure
  EnterDungeon
```

施設利用の有無と冒険準備は Plan の列として扱い、Lifecycle は「Actor が今どのレイヤーで活動しているか」を表すだけにする。

### 施設入口接触判定

task_0003 で施設移動先は入口タイル中心ではなく、入口タイル中心から `BuildingFacingDirection` 方向へ半タイル分ずらした接触位置になる。そのため、施設利用可否と `IsInsideFacility` は `GridPosition == EntrancePosition` のみで判定しない。

以下のどちらかの既存構造に合う形で、Application 層に純粋な判定ヘルパーを用意する。

```csharp
public static bool IsTouchingEntrance(MapLayer layer, Facility facility, LayerPosition actorPosition)
{
    var entranceCenter = layer.GetCellCenter(facility.EntrancePosition);
    var touchPosition = FacilityEntranceNavigationTargetCalculator.Calculate(layer, facility);
    var threshold = layer.CellSizeMeters * 0.5f;

    return actorPosition.DistanceSquaredTo(entranceCenter) <= threshold * threshold ||
        actorPosition.DistanceSquaredTo(touchPosition) <= threshold * threshold;
}
```

`FacilityEntranceNavigationTargetCalculator.Calculate()` は task_0003 と同じ計算を使い、入口中心 + facing vector * `CellSizeMeters * 0.5f` を返す。

**理想設計**

入口接触判定は Application 層の静的ヘルパーではなく、施設配置データから生成される `FacilityInteractionPoint` を Domain Value Object として持つ。

```csharp
public readonly struct FacilityInteractionPoint
{
    public Guid FacilityId { get; }
    public LayerPosition Position { get; }
    public float Radius { get; }
    public BuildingFacingDirection Facing { get; }

    public bool Contains(LayerPosition actorPosition) { ... }
}
```

`Facility` は `EntrancePosition` の grid だけでなく、計算済みの `InteractionPoint` を公開する。NavMesh 目標、入口接触判定、ActorView 非表示判定はすべて同じ `InteractionPoint` を使う。

- 入口タイル中心は「建物構造上の入口」。
- `InteractionPoint.Position` は「Actor が触れる移動目標」。
- `InteractionPoint.Radius` は「到着・入室・利用開始の共通しきい値」。

これにより、入口判定の重複と、中心座標 / オフセット座標の不一致を防ぐ。

### AdvanceInnRecoveryOrchestrator の変更

**Inn 予約処理を入口到達後の施設相互作用へ移動**

変更前: `actor.Position.LayerId.Equals(MapLayerId.Ground)` のみで予約候補と判断していた。

変更後: さらに Inn 入口接触チェックを加える。

```csharp
// 既存の Ground レイヤーチェックに加えて以下を追加
var groundMap = worldState.GroundMap;
if (!FacilityEntranceInteractionService.IsTouchingEntrance(groundMap.Layer, inn, actor.Position))
{
    // 未接触: 今フレームはスキップ（次フレームで再チェック）
    continue;
}
```

`inn` は `guild.Facilities` から `FacilityType.Inn` で取得する。

`EnsureInnReservation()` は現在 `guild.Facilities` をループしているため、Inn を見つけた後にこのチェックを入れる。ループ内の処理順を維持しつつ入口チェックを追加すること。

Inn 予約は `AdvanceInnRecoveryOrchestrator` では作成しない。`AdvanceGroundFacilityTaskOrchestrator` が入口の interaction point まで移動し、`FacilityInteractionOrchestrator.UseInn()` が空室・待機列・料金支払いをまとめて処理する。

**理想設計**

`AdvanceInnRecoveryOrchestrator` は廃止し、Inn も他施設と同じ `IFacilityInteractionHandler` として実装する。

```csharp
public interface IFacilityInteractionHandler
{
    FacilityType FacilityType { get; }
    FacilityInteractionResult Execute(FacilityInteractionContext context);
}
```

Inn Handler:

- Actor が `RecoverAtInn` Need を持っている場合だけ実行する。
- 空き部屋があれば料金支払い、予約作成、Actor を `Interacting` にする。
- 空き部屋がなければ `WaitingForCapacity` を返し、Actor は入口接触位置で待機する。
- 回復完了時に Actor の HP/MP と所持金、Inn の所持金、予約状態を更新する。

予約処理は「Ground にいる Actor を探して予約する」のではなく、「Inn Interaction に入った Actor が予約を要求する」形にする。これが最も自然で、施設入口移動と利用処理の関係も明確になる。

### GeneralStore / EquipmentShop 利用処理

**理想設計**

売却・購入・装備切替を別々の UseCase として tick ごとに実行しない。施設入口で開始した Interaction の中で、施設別 Strategy が `FacilityTransactionPlan` を作り、`FacilityTransactionExecutor` が一括適用する。

```csharp
public sealed class FacilityTransactionPlan
{
    public IReadOnlyList<ItemStack> ActorSells { get; }
    public IReadOnlyList<ItemStack> ActorBuys { get; }
    public EquipmentChangePlan EquipmentChange { get; }
    public int ActorGoldDelta { get; }
    public int FacilityGoldDelta { get; }
}
```

GeneralStore Handler:

- `ActorSells`: 不要な非装備アイテムすべて。ただし店舗所持金で買い取れる範囲。
- `ActorBuys`: ポーション所持数が 2 になるまで。不足分のみ。
- 回復アイテムを「不要」として売らないルールは `InventoryDispositionPolicy` に集約する。

EquipmentShop Handler:

- `ActorSells`: 不要な未装備装備すべて。ただし店舗所持金で買い取れる範囲。
- `ActorBuys`: 現在武器より評価スコアが高い購入可能な最良武器 1 つ。
- `EquipmentChange`: 購入武器を装備し、旧武器をインベントリに戻す。戻せない場合は購入計画自体を作らない。

`ProcessFacilityUsageUseCase` は Rest / Meal / BuyItem / BuyEquipment の enum 分岐を持つ汎用処理ではなく、`FacilityTransactionExecutor` に置き換える。施設の種類ごとの判断は Handler に閉じ込め、Executor は在庫・所持金・イベント発行の整合性だけを見る。

### ActorViewDataStore の変更

`SyncActor()` 内で `IsInsideFacility` を評価・更新する。

```csharp
// 地上レイヤーの場合のみチェック
if (actor.Position.LayerId.Equals(MapLayerId.Ground))
{
    viewData.IsInsideFacility = IsTouchingAnyFacilityEntrance(
        worldState.GroundMap.Layer,
        worldState.Guild,
        actor.Position);
}
else
{
    viewData.IsInsideFacility = false;
}
```

`ActorViewDataStore` が現在 `IGameWorldState`（または `AdventurerGuild`・`GroundMap`）を参照できない場合は、DI で追加して解決する。既存の `SyncActor()` の引数や依存注入の既存パターンに合わせること。

`IsTouchingAnyFacilityEntrance()` は LINQ 必須ではない。既存パターンとパフォーマンスに合わせて実装してよい。

**理想設計**

`ActorViewDataStore` が `Guild` や `GroundMap` を参照して入室判定を再計算しない。`ActorPresenceService` が Domain/Application 側で Actor の表示状態を決定し、ViewData はその結果を投影するだけにする。

```csharp
public readonly struct ActorPresence
{
    public bool IsVisibleOnMap { get; }
    public Guid? InsideFacilityId { get; }
}
```

- `MovingToInteractionPoint`: 表示。
- `Interacting`: 非表示。
- `WaitingForCapacity`: 入口で待つなら表示、施設内待機なら非表示。これは InteractionResult が決める。
- Dungeon 内や他レイヤーの表示判定とも同じ `ActorPresence` に集約する。

ViewDataStore は `ActorPresence` を読むだけなので、施設入口判定ロジックが View 更新経路に漏れない。

### View 層の変更（ActorView 関連）

`ActorViewData.IsInsideFacility` フラグを参照し、`true` の場合は `ActorView.SetVisible(false)` を呼ぶ。

既存の `ActorView.SetVisible()` で `spriteRenderer.enabled` を切り替える実装がある。View 層 Presenter または EntryPoint で `actorViewData.IsInsideFacility` を監視（Observable または毎フレーム確認）して切り替えを行う。具体的な観測パターン（R3 の `Subscribe` または Update ループ）は既存の ActorView 更新パターンに合わせること。

**理想設計**

View は `IsInsideFacility` という施設固有フラグではなく、`ActorViewPresentationState` を購読する。

```csharp
public enum ActorViewPresentationState
{
    Visible,
    HiddenInsideFacility,
    HiddenInDungeonTransition,
    HiddenDespawned
}
```

Presenter はこの state を `ActorView.SetVisible()` や将来の入退室アニメーションに変換する。施設入室の見た目は「非表示フラグ」だけでなく、必要なら入口でフェードアウト、退室時にフェードインできるようにする。ただしロジック上の施設利用開始は `FacilityInteractionState.Interacting` で決まり、View アニメーション完了には依存させない。
