新規概念追加ゲート:

- `ActorStatusViewData` / `ActorEffectIconData`
  - 既存類似概念: `ActorViewData`
  - 意味差分: `ActorViewData` は Actor のワールド表示位置と Behavior 種別、`ActorStatusViewData` は UI 表示用の HP 比率と Effect summary。
  - 代替しない理由: 位置差分 DTO に HP / Effect を混ぜると更新契機と利用者が異なる。
  - 統合条件: Actor / Item / Projectile などの UI 表示 DTO が共通 read model に整理された場合。
- `ActorDetailDto`
  - 既存類似概念: `ActorStatusViewData`
  - 意味差分: 選択 Actor の詳細表示用 snapshot。常時頭上表示とは利用者と情報量が異なる。
  - 代替しない理由: 頭上ステータスに詳細情報を持たせると常時 UI 更新の責務が膨らむ。
  - 統合条件: M8 以降で Actor detail UI の read model が共通化された場合。
- `PlayerEventLogEntry` / `PlayerEventLogStore` / `PlayerEventLogFormatter`
  - 既存類似概念: `GameEventHistoryService`
  - 意味差分: `GameEventHistoryService` はイベント履歴、PlayerEventLog はプレイヤー向け表示文と表示件数の一時 UI store。
  - 代替しない理由: GameEvent DTO に表示文字列を持たせない方針と、直近表示用の寿命が異なる。
  - 統合条件: Player 向けログ履歴とゲームイベント履歴の read model が正式に統合された場合。
- `WorldAddressableViewFactory`
  - 既存類似概念: `VisualConfigLoader`
  - 意味差分: `VisualConfigLoader` は Sprite / Material 設定、`WorldAddressableViewFactory` は Prefab を Addressable からロードして Pool / Presenter に供給する。
  - 代替しない理由: Prefab scope の寿命と VisualConfig の責務が異なる。
  - 統合条件: World View 全体の Addressable ロード責務を統合する専用 View asset repository が設計された場合。

## レビュー結果

### 1. 自動生成ファイルを staged diff で直接変更している

重大度: 重大

問題:

`DungeonInnModuleSceneId.g.cs` が staged diff に含まれており、`WorldUI` の定義が追加されている。このファイルは `// This file is generated by SceneIdGenerator.` と明記された生成物であり、`lighthouse-patterns.md` の hard gate「LighthouseGenerated 以下の `.g.cs` を手動編集していない」に抵触する。

原因:

`WorldUI` ModuleScene の追加時に、Lighthouse の SceneIdGenerator による再生成ではなく、生成済み `.g.cs` を差分として直接更新した状態になっている。生成物の変更自体は必要だが、生成元・生成手順の証跡がないため、次回生成時に上書きされるリスクと hard gate 違反が残る。

解決案:

Lighthouse の `SceneIdGenerator` を Unity Editor / uLoop 経由で実行し、`DungeonInnModuleSceneId.g.cs` が生成結果として同じ内容になることを確認する。生成後に staged diff が残るのは許容できるが、手動編集ではなく generator 出力であることを task log または review response に記録する。もし generator が `WorldUI` を検出できない場合は、Build Settings / scene path / ModuleSceneBase 配置を先に修正する。

根拠となるファイルリスト:

- `Client/Assets/DungeonInn/Runtime/Scripts/LighthouseGenerated/DungeonInnModuleSceneId.g.cs`
- `Client/Assets/DungeonInn/Runtime/Scene/ModuleScene/WorldUI.unity`
- `docs/guidelines/lighthouse-patterns.md`

完了条件:

- [ ] uLoop / Unity Editor 経由で Lighthouse SceneIdGenerator を実行している
- [ ] `DungeonInnModuleSceneId.g.cs` の `WorldUI` 追加が generator 出力として再現されている
- [ ] task log または本レビュー対応ログに生成実行結果を記録している
- [ ] `.g.cs` を手動編集しただけの状態ではないことを確認している

### 2. Actor 詳細 Popup が M7 の ScreenStack Popup 方針から外れている

重大度: 高

問題:

M7 roadmap の Phase 6b は Actor 詳細パネルを ScreenStack Popup として push / pop する方針を明記している。一方、現行 staged diff では `ActorDetailPopupPresenter` が Addressable から得た `ActorDetailPopup` prefab を `UnityEngine.Object.Instantiate` し、Canvas 子として直接保持している。これは M7 roadmap の「ScreenStack Popup」と一致しない。また `lighthouse-patterns.md` は ScreenStack / Modal を手動 `Instantiate` / `Destroy` で管理しないことを hard gate にしている。

原因:

M7 中に ActorDetailPopup を毎フレーム Actor 横へ追従させる要件と、ScreenStack Popup の生成・寿命管理の噛み合わせが未整理のまま、HUD Canvas 上の direct view として実装された。後続の Addressable 化により LifetimeScope の直参照は解消されたが、ScreenStack 経由の開閉契約までは回復していない。

解決案:

M7 の完了条件を満たすには、`ActorDetailPopup` を ScreenStack Popup として登録し、`ActorDetailPopupPresenter` は Popup の open / close と表示 DTO 更新の入口だけを持つ構造に戻す。毎フレームの位置追従が ScreenStack と相性が悪い場合は、少なくとも「ScreenStack Popup ではなく WorldUI HUD Panel とする」設計変更を M7 roadmap / task / review log に明示し、Lighthouse hard gate 上の例外として妥当かをユーザー判断に戻す必要がある。

根拠となるファイルリスト:

- `docs/roadmap/milestone7-roadmap.md`
- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/MainScene/World/ActorDetailPopupPresenter.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/MainScene/World/ActorDetailPopup.cs`
- `docs/guidelines/lighthouse-patterns.md`

完了条件:

- [ ] `ActorDetailPopupPresenter` が `UnityEngine.Object.Instantiate` で Popup View を直接生成していない
- [ ] ScreenStack Popup として実装する場合、ScreenStack の open / close 経由で Actor 詳細が表示される
- [ ] HUD Panel として維持する場合、M7 roadmap / task log に設計変更理由と hard gate 例外可否が記録されている
- [ ] どちらの方針でも Actor 選択解除時に View が閉じ、Presenter 以外が View 実体を操作できない

### 3. UI Presenter が広い `IGameWorldStateReader` を直接読み、M7 の narrow query 方針を満たしていない

重大度: 高

問題:

M7 roadmap は「UI 表示用の派生値は Application 層の narrow query / read model / DTO で用意し、View が広い `IGameWorldStateReader` を直接読んで集計しない」としている。しかし `WorldActorStatusPresenter` は毎フレーム `worldState.Actors` を直接走査し、`ActorDetailPopupPresenter` は `worldState.FindActor()` で位置を取得している。どちらも View / Presenter が Application 内部用の広い Reader を直接受け取っているため、`application-boundary-guidelines.md` の hard gate に抵触する。

原因:

HP / Effect の値自体は `GetActorStatusSummaryQuery` / `GetActorDetailQuery` に分離されたが、Actor の一覧・位置・Layer root 解決に必要な情報は Presenter が広い WorldState から補完している。表示位置 DTO または selection/detail 用 narrow query が不足している。

解決案:

Application 層に UI / View 専用の narrow read model を追加する。例として、頭上ステータスは `IActorStatusViewDataProvider` が active actor の status + position snapshot を返すか、`GetVisibleActorStatusViewsQuery` のような Query が `ActorStatusViewData` に `LayerPosition` を含めて返す。詳細 Popup は `GetActorDetailQuery` または別の `GetSelectedActorPopupQuery` が content と `LayerPosition` を同時に返し、Presenter は DTO と Camera / Layer mapper だけで位置を計算する。Presenter から `IGameWorldStateReader` を外す。

根拠となるファイルリスト:

- `docs/roadmap/milestone7-roadmap.md`
- `docs/guidelines/application-boundary-guidelines.md`
- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/MainScene/World/WorldActorStatusPresenter.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/MainScene/World/ActorDetailPopupPresenter.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/Application/World/GetActorStatusSummaryQuery.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/Application/World/GetActorDetailQuery.cs`

完了条件:

- [ ] `WorldActorStatusPresenter` の constructor から `IGameWorldStateReader` が消えている
- [ ] `ActorDetailPopupPresenter` の constructor から `IGameWorldStateReader` が消えている
- [ ] Actor status / detail popup に必要な Actor 位置が Application の narrow query / read model / DTO から提供されている
- [ ] View / Presenter が WorldState の Actor 集約を直接走査していない
- [ ] 既存の UI 表示テストまたは新規 EditMode test で DTO 生成が検証されている

### 4. Actor 頭上ステータスの更新が毎フレーム全 Actor query になっている

重大度: 中

問題:

`WorldActorStatusPresenter.UpdatePositions()` は毎フレーム `worldState.Actors` を全走査し、各 Actor ごとに `GetActorStatusSummaryQuery.Query(actor.Id)` を呼ぶ。この query は ActorEffect を列挙し、Effect がある場合は `effectBuffer.ToArray()` を行う。M7 roadmap は「HP / Effect 更新は変化した Actor のみに絞る」としており、Frame Loop での全件集計や allocation を避ける方針とズレている。

原因:

位置追従は毎フレーム必要だが、HP / Effect summary の更新頻度と分離されていない。位置更新と status content 更新が同じループにまとまっているため、位置追従の必要性に引きずられて status query も毎フレーム実行されている。

解決案:

ActorStatusView の位置更新と内容更新を分離する。位置更新は active view の ActorId と cached position snapshot を使って毎フレーム実行し、HP / Effect は `ActorViewDataStore` の dirty / event / revision 経由で変化した Actor のみ更新する。最低限、`GetActorStatusSummaryQuery` の結果を ActorId ごとにキャッシュし、Actor の HP / Effect 変更イベントまたは dirty id が来たときだけ再生成する。

根拠となるファイルリスト:

- `docs/roadmap/milestone7-roadmap.md`
- `docs/guidelines/application-boundary-guidelines.md`
- `docs/guidelines/implementation-quality-guidelines.md`
- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/MainScene/World/WorldActorStatusPresenter.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/Application/World/GetActorStatusSummaryQuery.cs`

完了条件:

- [ ] 毎フレームの頭上ステータス処理で HP / Effect summary を全 Actor 分再生成していない
- [ ] 位置追従と status content 更新の実行契機が分かれている
- [ ] `GetActorStatusSummaryQuery.Query()` が Frame Loop の全 Actor 走査から呼ばれていない
- [ ] ActorEffect がある Actor で毎フレーム `ToArray()` allocation が発生しない

### 5. WorldUI Canvas 取得が scene 検索と fallback 常駐生成に依存している

重大度: 中

問題:

`WorldHudCanvasProvider.Initialize()` は `Object.FindFirstObjectByType<WorldUIModuleScene>()` で ModuleScene を検索し、見つからない場合は `DontDestroyOnLoad` な fallback Canvas を生成する。M7 の `WorldUI` ModuleScene 追加意図は Canvas を ModuleScene に置くことであり、正規経路が見つからない場合に fallback で継続すると、SceneGroup 設定漏れや WorldUI ロード失敗を検知しにくい。

原因:

MainScene 側の Presenter が WorldUI の Canvas を必要としている一方、現行 LifetimeScope 構造では WorldUILifetimeScope と WorldLifetimeScope の親子関係がなく、DI 経由で Canvas を受け渡す経路がない。そのため scene object 検索と fallback に寄っている。

解決案:

M7 内で対応するなら、fallback を warning 付きの開発保険に限定し、PlayMode / test で World 遷移時に `WorldUIModuleScene.HUDCanvas` が見つかることを検証する。根治は M8 で予定した `WorldGameLifetimeScope` を親に置く構造へ移行し、WorldUI 側 Presenter / Provider が親 scope の Query / Event を受ける形にする。

根拠となるファイルリスト:

- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/MainScene/World/WorldHudCanvasProvider.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/View/Scene/ModuleScene/WorldUI/WorldUIModuleScene.cs`
- `Client/Assets/DungeonInn/Runtime/Scripts/Core/SceneGroupProvider.cs`
- `docs/roadmap/milestone8-roadmap.md`
- `docs/guidelines/lighthouse-patterns.md`

完了条件:

- [ ] World 遷移時に `WorldUIModuleScene.HUDCanvas` が正規経路で取得できることを PlayMode ログまたはテストで確認している
- [ ] fallback Canvas が使われた場合に Warning が出る
- [ ] fallback Canvas が scene unload / scope dispose 後に残留しない
- [ ] M8 の `WorldGameLifetimeScope` 分離タスクで fallback 経路の削除条件が追跡されている

## 総合判定

現時点では、Milestone 7 の表示要素自体は概ね実装されているが、次の理由で「次のマイルストーンへ進める状態」とはまだ判定しない。

- `.g.cs` 生成物の扱いが hard gate に抵触している。
- ActorDetailPopup が M7 roadmap の ScreenStack Popup 方針と一致していない。
- UI Presenter が `IGameWorldStateReader` を直接受け取り、M7 の narrow query 方針から外れている。

まず上記 1〜3 を優先対応し、その後に同じ観点で再レビューする。
