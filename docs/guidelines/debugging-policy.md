# デバッグポリシー

このドキュメントは、不具合調査時に利用する手順書であり、デバッグ時に陥りがちな非効率的なワークフローを防ぎ、観測事実に基づいて原因を特定するための恒久ルールを定義する。

デバッグの目的は、もっとも早く修正することではなく、再発しない形で原因と修正範囲を確定することである。仮説は必要だが、仮説を事実として扱ってはならない。

> **AGENTS.md との関係:**
> ユーザーが「〇〇したら治った」と具体的な修正方法を提示した場合は、まずそれを実装してテストする（AGENTS.md 問題解決アプローチ 1 が優先）。
> それ以外のバグ報告では、本ポリシーのフローに従う。

---

## ハードゲート

以下を全て満たしてから修正実装へ進むこと。

- [ ] ユーザーが提示した再現条件で実際に確認してから原因を特定した
- [ ] 観測または聞き取り結果に基づいて修正方針を決定した（「おそらく」「たぶん」「構造上そう見える」だけを根拠にしていない）
- [ ] 観測前の仮説をユーザーへ修正方針として提示していない
- [ ] 時間条件がある現象では、ユーザーが提示した待機時間・確認間隔を守って確認した
- [ ] ログ追加、計測、スクリーンショット、uLoop、テストのいずれかで現象の発生有無を確認した
- [ ] 一時的な診断コード、診断イベント、過剰ログを本修正後に削除した
- [ ] 観測結果と推測を明確に分けて報告した
- [ ] 既存の不具合と別の新規問題を発見した場合、混ぜて修正せず影響範囲を分離した

## 基本原則

基本原則は「なぜそうするか」の理由を定義する。具体的な手順は「推奨フロー」を参照。

### 1. 聞き取りは事実と予測を分けて行う

バグ報告を受けた時点で、ユーザーの報告に含まれる情報を以下の2種類に分類する。

- **観測事実**: ユーザーが実際に画面・ログ・動作で確認したこと
- **ユーザーの解釈・推測**: ユーザーが「こうなっているはず」「これが原因だと思う」と考えていること

これらが混在したまま調査を進めると、ユーザーの解釈を事実として扱い、誤った方向に調査が進む。

コードを読んで原因の見当がついた場合も、それはコードから導いた仮説であり、ユーザーが観測した事実ではない。コードに基づく仮説と、ユーザーの観測事実は別物として扱う。報告に事実と解釈が混在していると判断した場合は、必ず分けて確認する。

### 2. 修正方針は観測事実に紐づける

修正に入る前に、最低限以下を説明できる状態にする。

- 何を観測したか
- どのログ、スクリーンショット、テスト、コード行が根拠か
- その観測から何が確定したか
- まだ確定していないことは何か
- 修正対象がなぜその範囲に限定できるか

### 3. ユーザーの実機観察を事実として扱う

ユーザーが実機で見た現象に対して、「その理屈では説明できない」「現象が再現しないはず」と判断した場合は、ユーザーによって実際に観測された現象なのか、ユーザーによる予測なのかを確認する。

### 4. 仮説は調査の入口であり、結論ではない

仮説を立てること自体は必要だが、「仮説が正しいか」を確認するまでは修正方針として提示しない。

悪い例:

```text
戦闘開始時だけ通常移動が残っていると思われるので、開始時に止めます。
```

良い例:

```text
戦闘中に通常移動が同時に走っている可能性があります。
まず通常移動と戦闘移動の両方にActor ID、状態、移動前後座標を出して、
同一Actorで同一時間帯に両方が発生しているか確認します。
```

### 5. 一時診断コードは本修正に残さない

原因確認のためにログ、イベント、DTO、Debug Presenter購読などを追加してよい。ただし、目的は観測であり、恒久API追加ではない。

本修正後に確認すること:

- 一時診断イベントやDTOが残っていない
- 過剰な毎フレームログが残っていない
- 診断ログ用の依存やusingが残っていない
- 本当に恒久ログとして残す場合、ログレベル、頻度、出力条件、運用意図が説明できる

## 推奨フロー

推奨フローは「どう動くか」の手順を定義する。

### 1. 事実と予測を分けて聞き取る

バグ報告を受けたら、まず以下を整理する。情報が不足している場合は、過不足なく補う質問をユーザーに行う。

聞き取り項目:

- **観測事実（必須）**: 実際に画面・ログ・動作で確認したこと
- **ユーザーの解釈・推測（必須）**: 「こうなっているはず」「これが原因だと思う」などの解釈・推測
  - ユーザーの解釈がコードの調査方針に先行しないよう、観測事実とは明示的に分離して受け取る
- どのようなタイミングで発生したか
- 同じシチュエーションで必ず発生するのか
- 実行から遭遇までのプレイ時間はどれぐらいか
- AIだけで再現・観測できそうか

### 2. 現象を整理する

聞き取り結果をもとに以下を整理する。

- 発生条件
- 発生までの時間
- 期待される挙動
- 実際の挙動
- 影響を受けるEntityや画面
- ユーザーが確認済みの観測事実（ユーザーの解釈とは分離して記載する）

### 3. 観測ポイントを決める

「どの状態が同時に起きていれば仮説が正しいと言えるか」を先に決める。

例:

```text
戦闘移動と通常移動の二重適用を疑う場合:
- ActorId
- Actor名
- ライフサイクル状態
- 戦闘ターゲット有無
- 移動種別
- 移動前座標
- 移動後座標
- 目的地
- delta time
を同じフォーマットで出す。
```

観測に使える手段:

- uLoop PlayMode 実行
- `uloop.cmd get-logs`
- 一時的な診断ログ
- スクリーンショット
- Hierarchy / GameObject 状態確認
- EditMode / PlayMode テスト
- 対象ActorやEntityの座標、状態、ID、ターゲット、ライフサイクル状態の時系列記録

### 4. ユーザー提示の再現時間を守って確認する

時間経過で発生する現象では、短時間ログで結論を出さない。
ユーザーが「1分以上後に発生する」「5分まで確認してほしい」のように時間条件を提示した場合、その条件に合わせて確認する。

例:

```text
ユーザー指定: 1分以上後に確認できる。最大5分、1分ごとに確認。

実施:
- 1分時点: ログ確認
- 2分時点: ログ確認
- 再現した時点で観測内容を報告
- 必要があればPlayModeを停止して修正
```

再現した時点で確認目的を満たした場合は、最大時間まで待ち続ける必要はない。ただし、その理由をユーザーに報告する。再現しなかった場合も、確認した時刻と条件を報告する。

### 5. 観測結果を報告する

報告では、事実と解釈を分ける。

```text
観測事実:
- 2分時点で Actor A に NormalReturning が出た
- 同じActorに CombatApproach も出た
- NormalReturning は hasTarget=True だった

ここから確定できること:
- 戦闘対象を持つReturning中Actorに通常帰還移動が走っている

まだ未確定:
- 他のLifecycleStateでも同じことが起きるか
```

### 6. 最小ではなく適切な修正を選ぶ

観測で確定した原因に対して、既存設計と責務に沿う修正を選ぶ。

「差分が小さい」ことは理由にならない。既存guidelineに適切な責務配置、命名、設計境界がある場合はそれに従う。

### 7. 再発防止を追加する

修正後は、可能な限り再発防止のテストを追加する。

テストが難しい場合は、難しい理由を明記し、代替確認を行う。

- EditModeテスト
- PlayMode確認
- uLoopログ確認
- スクリーンショット比較
- 再現手順に沿った手動確認

## ログ追加ルール

### 一時ログ

一時ログは原因確認のために追加してよい。

条件:

- 何を確認するためのログか明確である
- ActorId / EntityId など相関できる情報を含む
- 時系列で比較できる
- 再現後に削除する

### 恒久ログ

恒久ログとして残してよいのは、運用上の異常、フォールバック、データ欠損、重要な状態遷移など、リリース後にも意味があるものに限る。

毎フレーム、Actorごと、Itemごとの大量ログは、原則として恒久ログにしない。

### Warningを出すべきケース

以下は正常系ではないため、利用された場合にWarningを出す。

- Fallback asset
- Placeholder asset
- 設定欠落時のデフォルト設定
- Addressables / ScriptableObject / TextTable などのロード失敗後の代替処理

## 報告フォーマット

不具合調査の報告は、以下の形を基本とする。

```md
確認したこと:
- ...

観測事実:
- ...

確定できる原因:
- ...

未確定のこと:
- ...

対応方針:
- ...

確認方法:
- ...
```
