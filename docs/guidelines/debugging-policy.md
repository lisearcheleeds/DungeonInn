# デバッグポリシー

このドキュメントは、不具合調査時に「推測を根拠に修正方針を決める」ことを防ぎ、観測事実に基づいて原因を特定するための恒久ルールを定義する。

デバッグの目的は、もっとも早く修正することではなく、再発しない形で原因と修正範囲を確定することである。仮説は必要だが、仮説を事実として扱ってはならない。

---

## ハードゲート

以下に該当する場合は、修正実装へ進む前に観測・記録・ユーザー確認を行うこと。

- [ ] ユーザーが具体的な現象、再現条件、発生タイミングを提示しているのに、その条件で確認せずに原因を断定していない
- [ ] 「おそらく」「たぶん」「構造上そう見える」だけを根拠に修正方針を決定していない
- [ ] 現象確認前の仮説を、ユーザーへ修正方針として提示していない
- [ ] 再現に時間がかかる現象では、ユーザーが提示した待機時間・確認間隔を守っている
- [ ] ログ追加、計測、スクリーンショット、uLoop、テストのいずれかで、現象の発生有無を確認している
- [ ] 一時的な診断コード、診断イベント、過剰ログを本修正後に残していない
- [ ] 観測結果と推測を明確に分けて報告している
- [ ] 既存の不具合と別の新規問題を発見した場合、混ぜて修正せず、影響範囲を分離している

---

## 基本原則

### 1. 観測を先に置く

不具合調査では、コード構造から原因を推測する前に、現象が本当に起きていることを観測する。

観測に使える手段:

- uLoop PlayMode 実行
- `uloop.cmd get-logs`
- 一時的な診断ログ
- スクリーンショット
- Hierarchy / GameObject 状態確認
- EditMode / PlayMode テスト
- 対象ActorやEntityの座標、状態、ID、ターゲット、ライフサイクル状態の時系列記録

ユーザーが「1分以上後に発生する」「5分まで確認してほしい」のように時間条件を提示した場合、その条件は仕様と同じ重みで扱う。短時間で再現しなかったことを根拠に否定してはならない。

### 2. 仮説は仮説として扱う

仮説は調査の入口であり、結論ではない。

悪い例:

```text
戦闘開始時だけ通常移動が残っていると思われるので、開始時に止めます。
```

良い例:

```text
戦闘中に通常移動が同時に走っている可能性があります。
まず通常移動と戦闘移動の両方にActor ID、状態、移動前後座標を出して、同一Actorで同一時間帯に両方が発生しているか確認します。
```

### 3. 修正方針は観測事実に紐づける

修正に入る前に、最低限以下を説明できる状態にする。

- 何を観測したか
- どのログ、スクリーンショット、テスト、コード行が根拠か
- その観測から何が確定したか
- まだ確定していないことは何か
- 修正対象がなぜその範囲に限定できるか

### 4. ユーザーの実機観察を事実として扱う

ユーザーが実機で見た現象は、まず事実として扱う。

「その理屈では説明できない」「現象が再現しないはず」と判断した場合でも、ユーザー観察を否定するのではなく、観測方法を見直す。

### 5. 一時診断コードは本修正に残さない

原因確認のためにログ、イベント、DTO、Debug Presenter購読などを追加してよい。ただし、目的は観測であり、恒久API追加ではない。

本修正後に確認すること:

- 一時診断イベントやDTOが残っていない
- 過剰な毎フレームログが残っていない
- 診断ログ用の依存やusingが残っていない
- 本当に恒久ログとして残す場合、ログレベル、頻度、出力条件、運用意図が説明できる

## 推奨フロー

### 1. 現象を整理する

以下を短く整理する。

- 発生条件
- 発生までの時間
- 期待される挙動
- 実際の挙動
- 影響を受けるEntityや画面
- ユーザーが既に確認した事実

### 2. 観測ポイントを決める

「どの状態が同時に起きていれば仮説が正しいと言えるか」を先に決める。

例:

```text
戦闘移動と通常移動の二重適用を疑う場合:
- ActorId
- Actor名
- ライフサイクル状態
- 戦闘ターゲット有無
- 移動種別
- 移動前座標
- 移動後座標
- 目的地
- delta time
を同じフォーマットで出す。
```

### 3. ユーザー提示の再現時間を守って確認する

時間経過で発生する現象では、短時間ログで結論を出さない。

例:

```text
ユーザー指定: 1分以上後に確認できる。最大5分、1分ごとに確認。

実施:
- 1分時点: ログ確認
- 2分時点: ログ確認
- 再現した時点で観測内容を報告
- 必要があればPlayModeを停止して修正
```

### 4. 観測結果を報告する

報告では、事実と解釈を分ける。

```text
観測事実:
- 2分時点で Actor A に NormalReturning が出た
- 同じActorに CombatApproach も出た
- NormalReturning は hasTarget=True だった

ここから確定できること:
- 戦闘対象を持つReturning中Actorに通常帰還移動が走っている

まだ未確定:
- 他のLifecycleStateでも同じことが起きるか
```

### 5. 最小ではなく適切な修正を選ぶ

観測で確定した原因に対して、既存設計と責務に沿う修正を選ぶ。

「差分が小さい」ことは理由にならない。既存guidelineに適切な責務配置、命名、設計境界がある場合はそれに従う。

### 6. 再発防止を追加する

修正後は、可能な限り再発防止のテストを追加する。

テストが難しい場合は、難しい理由を明記し、代替確認を行う。

- EditModeテスト
- PlayMode確認
- uLoopログ確認
- スクリーンショット比較
- 再現手順に沿った手動確認

## ログ追加ルール

### 一時ログ

一時ログは原因確認のために追加してよい。

条件:

- 何を確認するためのログか明確である
- ActorId / EntityId など相関できる情報を含む
- 時系列で比較できる
- 再現後に削除する

### 恒久ログ

恒久ログとして残してよいのは、運用上の異常、フォールバック、データ欠損、重要な状態遷移など、リリース後にも意味があるものに限る。

毎フレーム、Actorごと、Itemごとの大量ログは、原則として恒久ログにしない。

### Warningを出すべきケース

以下は正常系ではないため、利用された場合にWarningを出す。

- Fallback asset
- Placeholder asset
- 設定欠落時のデフォルト設定
- Addressables / ScriptableObject / TextTable などのロード失敗後の代替処理

---

## 長時間再現バグの扱い

時間経過で発生する不具合は、発生前のログだけでは判断しない。

必須事項:

- ユーザー指定の再現時間まで待つ
- 指定された間隔でログを確認する
- 再現した時点のログを保存または要点記録する
- 再現しなかった場合も、確認した時刻と条件を報告する

例:

```text
1分時点: 該当ログなし
2分時点: Actor A で該当ログあり
ここで原因仮説が検証できたため、5分まで継続せず修正に移る
```

再現した時点で確認目的を満たした場合は、最大時間まで待ち続ける必要はない。ただし、その理由をユーザーに報告する。

---

## 報告フォーマット

不具合調査の報告は、以下の形を基本とする。

```md
確認したこと:
- ...

観測事実:
- ...

確定できる原因:
- ...

未確定のこと:
- ...

対応方針:
- ...

確認方法:
- ...
```
